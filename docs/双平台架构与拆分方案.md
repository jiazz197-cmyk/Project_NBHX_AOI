# AOI 双平台架构与拆分方案

> 归属：全员（B 主笔架构、C 主笔公共包、A 主笔部署拓扑）；冻结：D2；变更窗口：D9 / D15。
> 依据：本文件是双平台边界的**唯一裁决来源**；接口细节见 `contracts/` 三份契约，排期见 `MVP开发计划.md`，骨架见 `P0骨架设计_双平台.md`。
> 最近一次结构性调整：**2026-09-09 模型分发改为镜像仓库 + 工位模板归 B**（原「A→B HTTP 下发模型/方案 + 心跳」作废）。

---

## 0. 结论速览

| 项 | 结论 |
|---|---|
| 平台数量 | 2 个，跨机器部署，各自独立前端 + 独立后端，可独立发版、独立重启 |
| 平台 A | **训练与标注平台**（`aoi-train`）：数据/字典/标注/预标注/训练/模型门禁/复审回流 + **模型发布到镜像仓库**；**不管理工位、相机、推理实例，不主动连接 B** |
| 平台 B | **推理与检测平台**（`aoi-infer`）：从镜像仓库拉取模型、**自行配置工位与工位模板（GUI）**、推理、错图统计/信息统计/日报、错图回传；**无 RBAC、无用户认证** |
| 公共部分 | **只有 `packages/skillname` 与 `packages/pipeline-core`** 两个纯 Python 包；无共享数据库、无共享中间件、无共享服务 |
| 模型分发 | A 把「ONNX 权重 + 模型能力描述 `model.yaml`」打成镜像推送到 **Docker Hub（或内网 registry）**；B 主动拉取并校验；A 不知道也不需要知道有哪些 B |
| 跨平台链路 | ① A→镜像仓库（发布）② B←镜像仓库（拉取）③ B→A 错图回传（HTTP，唯一直连） |
| 数据归属 | A：字典/数据集/标注/训练/模型注册/复审回流；B：工位/相机/工位模板/检测记录/图片/统计/日报 |
| 认证 | B 无用户体系与用户认证（内网）；B→A 回传带 `X-Internal-Token`；镜像仓库用 A 写凭据 / B 只读凭据 |
| 轻量约束 | B 不引入 Redis / Celery / MinIO / Nginx（可选）；单 Python 进程 + SQLite + 本地磁盘 + 静态前端 |
| 网络 | A **从不主动连 B**；B 出网拉镜像、回传错图；B 断网时用本地已有模型继续推理 |

## 1. 拆分动因

1. **部署位置不同**：训练/标注在中心机房（办公网、GPU 训练、数据资产）；推理/相机在产线现场（工控机/边缘服务器、靠近相机、7×24）。跨机器部署是既定事实，不应把产线运行绑在中心平台的可用性上。
2. **职责完全不同**：A 只负责「把数据变成模型」（标注/预标/训练/发布）；B 只负责「把模型跑起来」（拉模型/配工位/推理/统计/回传）。A 不关心产线怎么跑，B 不关心模型怎么训。
3. **资源与依赖不同**：A 需要 PostgreSQL + MinIO + Redis + Celery + GPU 训练；B 只需要一个 Python 进程 + SQLite + 本地磁盘 + 推理 GPU/CPU。强行共用基础设施会让 B 变重、把 A 的故障域扩散到产线。
4. **权限模型不同**：A 有操作员/管理员/超级管理员三角色与完整的**自研** RBAC；B 是现场运行看板与推理服务，**不需要用户体系，也不需要任何用户认证**。
5. **模型分发用镜像仓库最省事**：A 不主动连 B、不做实例管理、不做分片上传与断点续传；模型发布走标准容器镜像流程（版本、校验、离线包、回滚天然具备），B 拉取即可用。

## 2. 平台 A：训练与标注平台（`aoi-train`）

### 2.1 定位

数据资产与模型生产的**唯一主数据源**：负责「数据 → 模型」的全过程，产出物是**训练好的模型（含能力描述）**。
**不参与产线运行**：不管理工位、相机、推理实例，不推送模型到 B，不接收心跳。

### 2.2 职责

| 模块 | 内容 |
|---|---|
| core | **自研 RBAC**：三角色（操作员/管理员/超级管理员）+ 权限点 + 授权表 + DRF 权限类；request_id、错误码 |
| datasets | 缺陷字典、label config 生成、导入包裹（去重/质检/元数据）、数据集版本与划分红线、LS data_export 包裹 |
| prelabel | 预标任务、**A 侧自实现 LS ML backend 协议**（`/api/prelabel/{task_id}/*`）、三桶路由统计 |
| training | 训练任务、门禁、ONNX 导出、模型注册与 lifecycle、审批、**模型发布（构建镜像 → 推送 registry）** |
| review | 错图接收（来自 B）、复审工作项、终裁、建议清单、坏图管理、回流 |
| audit | 关键操作审计日志（`aoi_audit.audit_log`） |
| reports | 数据/训练侧统计（可选，最后做） |

### 2.3 技术栈与部署

- 后端：Django + DRF（LS 1.x fork），PostgreSQL 15，MinIO，Redis 7 + Celery 5。
- 前端：LS 1.x web（React + TS）二开页面。
- 推理：预标注用 ONNX Runtime + `pipeline-core`，在 A 侧 Celery GPU worker 内执行。
- **模型发布**：Celery `publish` 队列内构建最小模型镜像并 `docker push`（CI 亦可用同一条流水线）。
- 部署：中心侧单机 Docker Compose（nginx + ls-backend + workers + pg + minio + redis）。

### 2.4 与原方案的差异

- **取消 sidecar**：ML backend 协议与预标推理归 A 自身。
- **方案模板 / 工位 / 实例 / 下发全部移出 A**：方案模板变成 B 的「工位模板」；工位与相机主数据归 B；不再有实例注册与心跳；不再有 HTTP 分片下发。
- **模型分发改镜像仓库**：A 发布 → Docker Hub/内网 registry ← B 拉取。
- 训练进度 SSE 由 A 提供（`GET /api/train/jobs/{id}/progress`）。

## 3. 平台 B：推理与检测平台（`aoi-infer`）

### 3.1 定位

产线现场的**在线推理与运行监控平台**。自包含、无 RBAC、无用户认证、尽量轻量；从镜像仓库拉取 A 发布的模型，自行配置工位与工位模板，按模板推理并产出统计、日报与错图回传。

### 3.2 职责

| 模块 | 内容 |
|---|---|
| models | 从镜像仓库拉取模型镜像 → 解包 `/model/*` → 校验 sha256 → 解析 `model.yaml` → 本地模型库；版本管理、预加载/卸载 |
| template | **工位模板（B 自管，GUI 编辑）**：每个工位绑定模型 + 类别子集 + 阈值 + 切片参数；校验与热加载 |
| inference | ONNX Runtime 适配器、按 `pipeline-core` 切片/合并/三档判定、多模型按对象分发 |
| camera | 相机/通道适配器（DirectorySource 仿真、真实 GigE/RTSP）、软触发采集、坏图登记 |
| records | 检测记录与图片本地存储、保留策略、查询 |
| stats | 错图统计、信息统计、按工位/时段/缺陷类聚合 |
| report | 日报生成（每日 00:10）、HTML 展示、CSV 导出、保留 90 天 |
| outbox | 错图回传队列、失败重试、断点补传、状态可视化 |
| ops | 健康检查、磁盘/GPU/队列水位、日志轮转、备份 |

### 3.3 技术栈（轻量基线）

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | FastAPI + Uvicorn（单进程） | 无 Django、无 RBAC、无多租户 |
| 数据库 | **SQLite（WAL）** | 可切 PostgreSQL（同一 ORM），MVP 默认 SQLite |
| 存储 | 本地磁盘 | 图片/缩略图/模型/日报，无 MinIO 依赖 |
| 模型获取 | **OCI/Docker Registry HTTP API v2**（httpx + tarfile） | 无 Docker daemon 依赖；若本机有 Docker，也可 `docker pull` + `docker cp` 兜底 |
| 定时任务 | APScheduler（进程内） | 日报、统计滚动、保留清理、outbox 重试 |
| 推理 | ONNX Runtime（CUDA EP 或 CPU） | FP32/FP16，`INSPECT_CONCURRENCY=2` |
| 计算内核 | `pipeline-core` + `skillname` | 与 A 共享的唯一代码层 |
| 前端 | Vite + React + TS + Ant Design 5 + ECharts | **独立前端**，不复用 LS web 组件；构建产物由 FastAPI 托管 |
| 部署 | Docker Compose 或 systemd + 静态目录 | 单机；无 Redis/Celery/MinIO/Nginx 依赖 |

### 3.4 无 RBAC、无用户认证的安全边界（必须写进运维手册）

1. B **不做用户体系、不做登录、不做任何用户认证、不做角色权限**；三角色 RBAC 只在平台 A 使用。B 的前端与全部业务接口（查询与写操作）在内网/产线网段直接可用。
2. **网络隔离是 B 的唯一安全边界**：仅部署在产线内网、不暴露公网；不开放数据库与数据目录。
3. 对外只有两类出站访问：拉取模型镜像（registry 只读凭据）、回传错图到 A（`X-Internal-Token`，由 A 校验）。
4. 写操作（相机配置、工位模板、工位启停、模型卸载、日报重生成、outbox 重推）不做二次口令，直接生效，但写入本地操作日志（`b_audit`，`actor=local`）。
5. 需要防误操作时，由部署方在反向代理层加 IP 白名单或基础认证（不属于 B 的应用层功能）。

### 3.5 轻量化硬约束（评审红线）

- 不引入 Redis、Celery、RabbitMQ、MinIO、Kafka、Nginx（可选）、K8s、Docker daemon（可选，见 §3.3）。
- 不引入 Django/DRF、不引入 LS 前端组件库。
- 数据库默认 SQLite；不得为 MVP 引入独立的 PostgreSQL 实例（需要时可切，但不是默认）。
- 进程数：1 个 Uvicorn 进程 + 进程内线程池；定时任务用 APScheduler，不另起 worker 服务。
- 前端首屏静态资源 ≤ 2MB（gzip 后），5 个页面；不做视频流与大屏。

## 5. 唯一公共层：`packages/`

> 原则：**公共部分只保留「跨平台语义」与「纯计算」**。凡是带框架、带业务表、带权限的代码一律不共享。

### 5.1 `packages/skillname`（词汇表，零三方依赖）

```python
# packages/skillname/skillname/__init__.py
class SkillName(str, Enum):                      # 兼容 Python 3.10（不用 enum.StrEnum）
    OBJECT_DETECTION = "ObjectDetection"        # MVP 唯一
    IMAGE_CLASSIFICATION = "ImageClassification" # 预留
    IMAGE_SEGMENTATION = "ImageSegmentation"     # 预留

# skillname → LS 控件映射（A 生成 label config 用；B 只做校验）
SKILL_TO_LS_CONTROL: dict[SkillName, str] = {
    SkillName.OBJECT_DETECTION: "RectangleLabels",
}

class ModelLifecycle(str, Enum):      # candidate / approved / published / retired
class DatasetSubset(str, Enum):       # train / val / test
class Verdict(str, Enum):             # auto_pass / recheck / manual（判定语义在 pipeline-core）

def is_valid_fault_code(code: str) -> bool          # ^[a-z][a-z0-9_]{0,27}_(0[1-9]|[1-9][0-9])$
def format_model_ref(seq: int, framework: str, dataset_version: str) -> str
def parse_model_ref(ref: str) -> ModelRef           # {seq}-{framework}@ds{version}
def image_tag_from_model_ref(ref: str) -> str       # 3-yolo@ds1 -> 3-yolo-ds1（镜像 tag 规范）
```

- 为什么独立成包：LS 上游 `ml_models.SkillNames` 只有 `TextClassification` / `NamedEntityRecognition`，**没有目标检测**；AOI 需要自建任务类型枚举（`ObjectDetection` → `RectangleLabels`），且 A/B 两侧必须用同一套 code / model_ref / skillname 规范。
- 依赖：仅 Python 标准库（`enum`/`re`/`dataclasses`），**不得引入 pydantic/django/fastapi**；`requires-python >=3.10`，枚举用 `(str, Enum)` 写法。

### 5.2 `packages/pipeline-core`（推理内核，框架无关）

```python
@dataclass(frozen=True)
class DetectBox:   xyxy: tuple[float, float, float, float]; class_id: int; object_code: str; score: float; model_ref: str = ""
@dataclass
class DetectResult: boxes: list[DetectBox]; tiling_meta: dict; verdict: str; verdict_reasons: list[str]
@dataclass
class ObjectSpec:   code: str; model_ref: str; class_map: dict[int, str]; recheck_min: float; auto_min: float; risk_level: int
@dataclass
class InspectConfig: objects: list[ObjectSpec]; tile_size: int = 1280; overlap: float = 0.2

class RuntimeModel(ABC):            # 推理后端由调用方注入
    def infer(self, tiles: list[np.ndarray]) -> list[list[RawBox]]: ...

def slice_image(img, tile_size=1280, overlap=0.2) -> list[Tile]
def box_to_global(box, offset) -> DetectBox
def merge_across_tiles(boxes, iou_thr=0.5) -> list[DetectBox]
def decide_verdict(boxes, cfg) -> tuple[str, list[str]]      # 宁错不漏，逐对象阈值
def run(image, cfg, models: Mapping[str, RuntimeModel]) -> DetectResult
def load_config(yaml_text: str) -> InspectConfig             # 检测配置（对象/阈值/切片）结构校验
class StubRuntimeModel(RuntimeModel)                         # 确定性假框，供 P0/测试
```

- **没有「方案模板 / 工位」概念**：`InspectConfig` 只是「对象 + 阈值 + 切片参数」的通用检测配置。A 的预标配置与 B 的工位模板都解析成 `InspectConfig` 后交给 `run()`。
- 依赖：`numpy` + `pillow`；`pyyaml` 为 `load_config` 的可选 extra（`pipeline-core[yaml]`）。**不依赖 onnxruntime**——A 与 B 各自提供 `OnnxRuntimeModel` 适配器。
- 版本策略：语义化版本（MVP `0.1.0` 起）；A/B 在交付时锁同一版本；破坏性变更需双端契约测试通过（`tests/contracts/`）。

### 5.3 为什么不再共享更多

| 候选 | 不共享的原因 |
|---|---|
| ORM 模型 / 表结构 | A 用 Django ORM + PostgreSQL；B 用 SQLAlchemy + SQLite。强行共享会把 Django 依赖带进 B |
| 请求/响应 Pydantic 模型 | A 用 DRF Serializer；B 用 Pydantic。共享需引入双方框架依赖，收益低 |
| 统一信封 / 错误码实现 | 语义共享（契约层），实现各写一份（各 30 行），避免跨平台版本耦合 |
| RBAC / 权限模型 | A 自研（`aoi_core`），B 无用户体系；共享会把 A 的授权模型带进 B |
| 工位模板 / 工位 / 相机 | B 自管（GUI 编辑），A 不参与产线运行；只通过 `InspectConfig` 结构间接对齐 |
| 事件总线 | B 轻量自包含，不接 Redis Streams；跨平台交互全部走镜像仓库 + 显式 HTTP 契约 |

## 6. 部署拓扑与跨机通信

### 6.1 拓扑

```
中心侧（办公网/机房）                        镜像仓库（Docker Hub / 内网 registry）
┌──────────────────────────────┐            ┌──────────────────────────┐
│ 平台 A                        │  ① 发布    │  <org>/aoi-model:<tag>    │
│  nginx:443/8080               │ ─────────▶ │  /model/model.onnx        │
│  ls-backend:8000 (Django)     │            │  /model/model.yaml        │
│  worker-gpu / worker-cpu      │            │  /model/model.onnx.sha256 │
│  PostgreSQL / MinIO / Redis   │            └────────────▲─────────────┘
└──────────────▲───────────────┘                         │ ② 拉取
               │ ③ 错图回传（B→A，唯一直连）               │
               │                            ┌────────────┴─────────────┐
               └────────────────────────────│ 平台 B（产线工控机/边缘）  │
                                            │  uvicorn:8990（API+前端） │
                                            │  sqlite + /data（本地）    │
                                            │  工位/相机/工位模板自管    │
                                            └────────────┬─────────────┘
                                                         │ GigE / RTSP / 目录仿真
                                                         ▼
                                                     相机 / 工位 ST01~ST08
```

- A 与 B **不在同一台机器**，不共享数据库、对象存储、Redis；**A 从不主动连 B**。
- B 可部署多实例（每条产线一个），每个实例自管工位与模板；A 侧无需登记，错图回传带 `instance_code` 便于溯源。
- 时间同步：两侧必须启用 NTP；B 上报 `captured_at`，A 记录 `received_at`；偏差 > 2s 告警。

### 6.2 端口与环境变量

| 侧 | 变量 | 说明 |
|---|---|---|
| A | `MODEL_REGISTRY` | 镜像仓库地址，如 `docker.io` 或 `registry.corp:5000` |
| A | `MODEL_IMAGE_REPO` | 模型镜像仓库名，如 `<org>/aoi-model` |
| A | `MODEL_REGISTRY_USER` / `MODEL_REGISTRY_PASSWORD` | 推送凭据（只给发布任务用） |
| A | `INTERNAL_TOKEN` | 校验 B→A 回传 |
| B | `MODEL_REGISTRY` | 同 A；默认 `docker.io` |
| B | `MODEL_REGISTRY_USER` / `MODEL_REGISTRY_TOKEN` | **只读**拉取凭据（匿名可拉公开仓库时可留空） |
| B | `MODEL_PULL_MODE` | `oci`（默认，纯 HTTP）或 `docker`（本机 Docker CLI） |
| B | `TRAIN_PLATFORM_BASE_URL` | A 的基址，如 `https://aoi-train.corp:8080` |
| B | `INTERNAL_TOKEN` | B→A 回传携带 |

### 6.3 网络与断连策略

| 场景 | 行为 |
|---|---|
| B 拉不到镜像仓库 | 继续用本地已有模型推理；模型库页显示拉取失败与重试；不阻塞产线 |
| A 长时间不可用 | B 正常推理/统计/日报；回传积压进 outbox，恢复后补传 |
| B 长时间离线 | A 无感知（A 不依赖 B）；A 侧无需任何处理 |
| 跨机时钟漂移 | 双时间戳：`captured_at`（B 采集时钟）+ `received_at`（A 接收时钟）；日报以 `captured_at` 为准 |
| 镜像仓库限流/鉴权失败 | 记录错误并退避重试；支持离线包（`docker save` / 层 tar）人工导入 |

## 7. 数据归属与流动

| 数据 | 归属 | 流动 |
|---|---|---|
| 缺陷字典 / 数据集 / 标注 / 训练任务 / 模型注册表 | A | 不流向 B（B 只拿到模型镜像里的能力描述） |
| 模型权重 + `model.yaml` | A 产出 | A→镜像仓库→B（B 本地落盘并校验 sha256） |
| 工位 / 相机 / 工位模板 | B | 留在 B；A 不持有工位主数据 |
| 检测记录（全量）/ 图片 / 统计 / 日报 | B | 留在 B；仅可疑图与坏图回传 A |
| 可疑图（`verdict != auto_pass`） | A（回传后） | B→A，A 落 `image` + `inspection_fact` + `review_workitem`；`station_code` 为 B 侧不透明字符串 |
| 坏图（采集/解码/推理失败） | A（回传后） | B→A，A 落 `bad_image` |
| 复审终裁 / 建议 / 回流数据 | A | 人工确认后以 `source=reflux_review` 进数据集候选（红线：不进测试集） |

> 幂等主键：跨平台回传以 `(station_code, seq)` 去重（`suspicious` 落 `inspection_fact`、`bad` 落 `bad_image`）；A 侧重复请求返回既有 id 并标记 `duplicated=true`。

## 8. 关键链路时序

### 8.1 模型发布（A → 镜像仓库）

```
A: 训练完成 → 门禁通过 → 金标准回归通过 → 人工审批(lifecycle=approved)
A: Celery publish 任务：构建模型镜像（/model/model.onnx + model.yaml + .sha256）→ docker push
A: 记录 model_publish{image, tag, digest, status=published}
A: lifecycle=published；可选打 latest 别名
```

### 8.2 模型拉取（B ← 镜像仓库）

```
B: 模型库页输入/选择镜像地址（或列出可拉取的 tag）
B: 拉取 manifest → 下载 layer → 解包 /model/* → 校验 sha256 → 解析 model.yaml
B: 注册 b_model（model_ref/skillname/classes/推荐阈值/digest）
B: 解析失败/sha256 不符 → 拒绝并报错，不影响已有模型
```

### 8.3 工位模板配置（B 本地 GUI）

```
B: 工位与相机页 → 选择工位 → 选模型（本地模型库）→ 勾选类别子集 → 调阈值 → 保存
B: pipeline-core.load_config 校验（code 合法/class_map 对齐/0<recheck_min<auto_min<1）
B: 校验通过 → 热加载到该工位；失败 → 提示字段级错误
```

### 8.4 推理与错图回传（B → A）

```
相机/模拟器 → POST {B}/api/v1/inspect/image
B: 解码 → pipeline-core.run(切片→推理→合并→三档判定) → 落 inspection
B: verdict != auto_pass 或坏图 → 写 outbox → 异步 POST {A}/api/ingest/findings
A: 图片落 MinIO → image 行 → inspection_fact → review_workitem / bad_image
A: → {fact_id, workitem_id, image_id, bad_image_id, duplicated}
B: outbox 标记 pushed
```

### 8.5 日报

```
APScheduler 00:10 → 聚合昨日 inspection/stats_daily → Jinja2 渲染 HTML → 落 /data/reports/{day}.html + CSV
前端「日报」页 → 列表 / 详情 / 导出
```

## 9. 与旧方案（LS 二开 + sidecar / A→B 直连下发）的差异对照

| 维度 | 旧方案 | 新方案 |
|---|---|---|
| 服务数 | LS 主应用 + sidecar；或 A + B 直连 | 平台 A + 平台 B（各自独立前后端），A 不连 B |
| sidecar | FastAPI 侧车，与 A 同机 | **取消**；预标归 A，在线推理归 B |
| 模型交付 | B 读 A 的 MinIO；或 A 分片 HTTP 推送 | **A 推镜像到 registry，B 主动拉取**（版本/校验/离线包天然具备） |
| 方案模板 | A 拥有方案模板并下发给 B | **B 自管工位模板**（GUI），A 只在 `model.yaml` 里给推荐阈值 |
| 工位主数据 | A 拥有 `aoi_system.station` | **B 拥有**，A 不持有 |
| 实例管理 / 心跳 | A 注册 B 实例、收心跳 | **完全取消**；A 无感知 |
| 检测事实 | sidecar 写 A 的 `/api/review/facts` | B 回传 `/api/ingest/findings`（仅可疑/坏图） |
| 认证 | sidecar 验 LS JWT；内部头 | B 无用户认证；B→A 内部头；registry 读写凭据 |
| 共享代码 | pipeline-core + events/trainers/exporters/common | 只保留 `skillname` + `pipeline-core`（`InspectConfig`） |
| 数据库 | 全部在 A 的 PG | A 用 PG；B 用独立 SQLite |
| 统计/日报 | A 侧报告（最后做、可砍） | **B 侧核心能力**（错图统计/信息统计/日报） |
| 断网可用性 | sidecar 与 A 同机 | B 断网用本地模型继续推理，回传积压补传 |

## 10. 二期演进（本期只冻结接口，不实现）

1. **私有 registry / OCI artifact**：用 `oras` 以 OCI artifact 形式发布模型（更小的元数据层），支持签名（cosign）与 SBOM。
2. **B 多实例集中视图**：由运维侧（而非 A）汇总各 B 的统计；A 仍不参与。
3. **视频级预览**：MJPEG/RTSP/WebRTC 独立媒体服务，不改变主架构。
4. **VLM 复审**：`RecheckBackend` 在 B 侧实现（Qwen3-VL 等），B 先出建议再由 A 终裁。
5. **高价值数据桶**：可疑图 + 终裁结果自动入 `hv-data/`，供 A 侧主动学习。
6. **B 自动升级**：离线升级包 + 版本签名校验。
7. **B 切 PostgreSQL**：单机数据量超过 SQLite 舒适区（> 5000 万行检测记录）时切换，ORM 层不变。
